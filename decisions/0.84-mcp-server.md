# 0.84 MCP server

- Decided by: user (TODO item 30 design and its open questions: bearer
  token and OAuth, MCP independent of AI provider access, read only switch
  off by default, the official SDK; the MCP tools are the assistant's tools
  except the ones that need the user's input, such as a password); Claude
  (details below)
- Date: 2026-10-21
- Builds on 0.83 (AI assistant tool catalog) and 0.85 (live updates).

## Connection

- Every user can add personal MCP clients in Profile → MCP clients and
  connect their own AI (Claude Code, Claude Desktop, claude.ai, ChatGPT,
  Cursor, ...). "No AI" and the provider settings of 0.83 do not affect it.
- `github.com/modelcontextprotocol/go-sdk` serves `POST /mcp` through
  `mcp.NewStreamableHTTPHandler` with `Stateless` and `JSONResponse`: no
  session id and no server-to-client requests. The handler is wrapped in
  `http.CrossOriginProtection` (the SDK's own option is deprecated). The
  SDK's DNS rebinding check is replaced by the same check that also admits
  `APP_URL`'s host: a reverse proxy on the same machine connects from a
  loopback address with the public `Host`, which the SDK refuses. The
  server and its tools are built per request for the caller.
- **Token** clients get a personal token (`nmcp_` + 32 random bytes,
  base64url), shown once, sent as `Authorization: Bearer`, valid until the
  client is deleted or the token regenerated (the old one is deleted).
- **OAuth** clients get a client id (16 random bytes, base64url) and a
  client secret (`nmcps_` + 32 random bytes), shown once, and a list of
  redirect URIs. Presets: Claude (`https://claude.ai/api/mcp/auth_callback`,
  `https://claude.com/api/mcp/auth_callback`) and ChatGPT
  (`https://chatgpt.com/connector_platform_oauth_redirect`). A redirect URI
  is `https`, or `http` on `127.0.0.1`, `[::1]` or `localhost`, whose port
  is ignored when matching (RFC 8252); anything else must match exactly.
  Regenerating the secret keeps the client's tokens: the secret alone
  gets no token without the user's consent.
- The token or secret goes only to the tab that created or regenerated it;
  then every tab of the user gets the response without it under a new
  request id (0.85).
- Tokens and client secrets are stored as hex SHA-256 hashes; `mcp_token`
  keeps the first characters as `token_prefix` to tell tokens apart.
  Timestamps are unix seconds like the other tables.

## OAuth 2.1 authorization server (`internal/http/oauth`)

- Issuer `APP_URL`. `/.well-known/oauth-authorization-server` (RFC 8414)
  and `/.well-known/oauth-protected-resource` (RFC 9728, resource
  `APP_URL/mcp`). Authorization code with PKCE `S256` only,
  `client_secret_basic` and `client_secret_post`, no dynamic client
  registration, no scopes.
- `GET /oauth/authorize` checks `client_id` and the redirect URI first; an
  error there shows the error page and never redirects. Then
  `response_type=code`, `code_challenge` with method `S256` and `resource`
  (when sent it must be `APP_URL/mcp`, RFC 8707) — errors here redirect
  with `error` and `state`. A valid request gets the SPA (the
  `SameSite=Strict` session cookie is not sent on the cross-site arrival,
  0.63). The page `oauth-authorize` sends a signed out user through login
  and back, reads `GET /api/oauth/consent?<query>` (client name, read only,
  signed in user) and posts `POST /api/oauth/consent` with
  `{query, allow}`, which answers `{redirect_url}`: the code, or
  `error=access_denied`. Both run behind the session middleware and
  `http.CrossOriginProtection`. A client acts as the user who created it,
  so another signed in user gets 403. The route has the meta flag
  `returnAfterSteps`: a user with a pending password reset comes back to
  the consent page after it (`ResetPasswordPage` follows `redirect`). In
  `make dev` Vite serves the page itself, so only the consent API checks
  the request; `/oauth/token`, `/.well-known` and `/mcp` are proxied.
- Codes: 32 random bytes, single use, 60 seconds, in memory (lost on a
  restart; the user connects again).
- `POST /oauth/token`: `authorization_code` (client authentication,
  `code_verifier`, same redirect URI) and `refresh_token`. Access tokens
  last 1 hour, refresh tokens 30 days and rotate on every use; a rotated
  refresh token used again deletes every token of the client. Failed client
  authentication counts in the login rate limit by address (0.51): every
  token request is an attempt and success never resets it, so a valid
  client cannot clear the limit of the login form. Errors
  follow RFC 6749 (`invalid_request`, `invalid_client`, `invalid_grant`,
  `unsupported_grant_type`).

## Acting as the user

- The bearer verifier hashes the token, checks its kind (personal or
  access) and expiry, loads the client and the user, and returns the user
  id. Every request builds the session from the user row
  (`requeststate.NewSession`), so a role change applies on the next call.
  A user who must reset their password gets 403. `last_used_at` is written
  at most once a minute. Deleting the user or the client deletes its
  tokens; expired tokens go in the hourly task `remove-expired-mcp-tokens`.
- `hub.Call(ctx, caller, namespace, type, payload)` runs the registered
  handler like `dispatch` does for a browser message, with an in-memory
  client that holds no connection slot (`MAX_CONNECTIONS_PER_USER`), and
  returns the response with the call's request id; other pushes are
  dropped. A `ClientError` or validation issues come back as a
  `*websocket.ClientError`. `RespondToUser` reaches the user's open tabs
  and the in-memory client, and change events (0.85) go out as for a
  browser call.

## Tools

- The 0.83 catalog filtered by the caller's role, run on the server by
  `aitools.Runner`: it validates the arguments, builds the message, calls
  `hub.Call` and trims the response. Browser tools are left out, since they
  need the user in the app or their password: `open_note`, `open_help`,
  `set_note_protection`, `add_passkey`, `delete_passkey`,
  `export_my_data`. Three browser tools get a server version instead:
  `get_profile` (from the session), `list_help_topics` and
  `get_help_topic` (from the exported help, below).
- Catalog tools carry `ReadOnly`. Annotations: `readOnlyHint` and
  `idempotentHint` for read only tools, `destructiveHint` for tools the
  assistant confirms (`Confirm`), so the AI client asks its user; NoteMe
  shows no Allow / Deny here.
- **Read only** is a per-client switch, off by default. On, `tools/list`
  has only read only tools and the runner refuses the rest.
- **Protected notes, never**: every response loses the `note` field of any
  object with `is_encrypted`; `get_note` and `get_history_version` add
  "This note is protected and cannot be read over MCP."; `update_note`
  checks the note first and refuses a protected one with "This note is
  protected and cannot be changed over MCP.". `encryptText`, `decryptText`
  and `verifyOwnPassword` are not in the catalog.
- Tool errors (client errors, validation issues, refusals) are results
  with `isError` and the message; other errors are logged and answer
  "Error while processing the request".

## Help over MCP

- `vite build` renders every help topic to markdown into
  `dist/help/<key>.md` and writes `dist/help/index.json`
  (`[{key, name, permission}]`, `permission` null or the settings
  permission an admin topic needs, 0.79). The binary embeds `dist`; a topic
  with a permission is listed when the role can access settings and has
  that permission, as `canSeeHelpTopic` does.
