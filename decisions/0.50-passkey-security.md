# 0.50 Passkey security

- Decided by: user (support every kind of passkey: security keys, phones,
  iCloud Keychain, Bitwarden; user verification preferred, not required;
  usernameless sign in kept by requiring passkeys the authenticator stores;
  password asked once and again after five minutes; errors the user can fix
  are shown; `@simplewebauthn/browser` on the browser side); Claude (the
  rest)
- Date: 2026-10-19

Backend: `internal/components/passkeys` (on `components.Passkeys`) wraps
go-webauthn and holds the pending ceremonies.

- Relying party: id = `APP_URL` host, the only accepted origin = `APP_URL`
  origin. WebAuthn does not allow an IP address as relying party id; with
  one the server starts, logs a warning, and passkey requests answer
  "Passkeys are not available on this server.".
- Registration options: attestation `none`, `residentKey: required`
  (`requireResidentKey: true`), `userVerification: preferred`, the user's
  passkeys as `excludeCredentials`, and the `credProps` extension. Sign in
  sends no username and no `allowCredentials`, so only passkeys stored on
  the authenticator can be offered there; a response whose `credProps`
  reports `rk: false` is refused ("This authenticator cannot store the
  passkey on the device, ..."). Browsers that do not report `credProps` are
  accepted, the `required` setting covers them.
- User verification is preferred on both ceremonies and not enforced, so
  keys without a PIN still work (user).
- Before options are handed out, `getPasskeyRegistrationOptions` needs the
  current password (`{password}`; without it the response is
  `{password_required: true}` and no options). A correct password is
  remembered for five minutes for that browser session (all its tabs, keyed
  by the session cookie, in memory), so registering several passkeys asks
  once. A wrong password is a validation issue on `password` ("Invalid
  password.") and every try counts against the login rate limit of the
  address (0.51). Not in the original, which added a passkey to any live
  session.
- Ceremonies (registration per session key, sign in per `request_id`) are
  valid five minutes, enforced by go-webauthn and by the store, and used
  once: verifying removes them whether it passes or fails. Each store holds
  at most 10 000 entries; when full, expired ones go first, then the one
  closest to expiring.
- Sign in: the credential is looked up by id, its owner must not be deleted,
  and the user handle in the response must be the owner's handle. The
  stored "can be backed up" flag must match (go-webauthn), the "is backed
  up" flag is updated after each use. A signature counter that does not
  increase (when either side is not 0) is rejected as a possible clone;
  synced passkeys always report 0 and pass.
- Errors: what the user can act on is shown ("Passkey registration has
  expired, please try again.", "This passkey is already registered to this
  or another account.", "Passkey sign in has expired, please try again.",
  the `credProps` refusal, "Invalid password.", the rate limit message).
  Library errors are only logged; the browser gets "Verification failed."
  for registration and "Could not verify your passkey, make sure it is
  registered to your account." for sign in.
- Passkey names: the default from the first matching transport as in the
  original; renaming trims the name and requires 1 to 255 characters (the
  original saved any name, including an empty one).
- Passkeys of a deleted user can no longer sign in. Removing them when a
  user is deleted belongs to user management (item 17).

Frontend:

- `@simplewebauthn/browser` (approved here, 0.11) builds the WebAuthn calls
  (`startRegistration`, `startAuthentication`). Closing the prompt or a
  timeout (`NotAllowedError`, `AbortError`) shows nothing; its error codes
  for an already registered device, an authenticator that cannot store
  passkeys, an unsupported algorithm and a wrong address get their own
  messages.
- Mock mode never opens the browser prompt, which would save real passkeys
  for localhost; the mock answers stand in for the browser.
- The login page keeps "Sign in" when WebAuthn is unsupported and hides only
  the passkey button (0.9.u).
- Passkeys live on their own Profile tab "Passkeys" (`/app/profile/passkeys`).
