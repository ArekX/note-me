# 0.61 One migration with the whole v2 schema

- Decided by: user (one migration holding the whole schema for v2; the app
  migrates on start; noteme-upgrade must work); Claude (details)
- Date: 2026-10-19
- Supersedes 0.52.

- `20231216_162457_initdb` is the only migration and holds the complete v2
  schema, including what `20261019_123255_passkey_security` added (0.49):
  `user.passkey_user_handle` with its unique index, `user_passkey` without
  `webauthn_user_identifier` and with `is_backup_eligible`, the unique index
  on `credential_identifier` and the index on `user_id`. It keeps the name
  original databases already record.
- `noteme-upgrade` brings any older database to exactly that structure and
  is safe to run again: original migration table converted, file blobs
  extracted and the column dropped (0.57), passkey tables restructured
  (old passkeys deleted, column dropped and added, indexes created), rows of
  migrations that no longer exist removed (an earlier Go database recorded
  `passkey_security`), old note encryption converted. A test compares the
  upgraded original schema with a fresh one column by column and index by
  index; the original schema it starts from is kept in
  `cmd/noteme-upgrade/testdata/original-schema.sql` and matches a database
  made by the Deno app.
- The server runs pending migrations at every start, as before; it and
  `noteme-cli migrate-up` now refuse a database that still needs the
  upgrade (original migration table, `file.data`, original passkey table, or
  a recorded migration that no longer exists) with the reason and "run
  noteme-upgrade first", instead of running on a half-compatible database.
- Until v2 is released, a structure change edits this migration and extends
  `noteme-upgrade` so older databases reach the same structure.
