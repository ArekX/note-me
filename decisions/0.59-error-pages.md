# 0.59 Error pages and layout check

- Decided by: Claude (TODO item 21)
- Date: 2026-10-19

- In the SPA the 403 and 500 pages matter where a browser lands on a server
  URL directly: a file link, or an export or backup download opened in a
  tab. Those routes answered JSON, which the browser showed as raw text.
  Now, when the request asks for HTML (`Accept: text/html`, which browsers
  send for navigations and `fetch` from the app does not), errors redirect
  (303) to `/error/403`, `/error/404` (also for 400) or `/error/500`; API
  clients keep the JSON body. An anonymous visitor of a private file is
  still sent to the login page (0.48).
- `/error/:status` shows a fixed title and text per status in the original's
  layout (status, title, red message box, "Go back"); nothing from the URL is
  displayed, so a crafted link cannot put its own message on the page.
  `ErrorPage` is shared with the 404 page, which keeps its plain text.
- A page whose code fails to load (`router.onError`, for example after an
  update while the tab was open) shows the 500 page. The error route skips
  the auth guard, so a failing session request cannot loop.
- Settings without any settings permission still go to the dashboard
  (0.44), so no in-app 403 page is used there.
- Checked against the original and already in place from earlier items:
  wallpaper on the login page and blended into the sidebar, the mobile 2×2
  sidebar grid and the desktop menu order (settings, bell, profile, lock,
  help, logout), editor buttons moving into the menu below `xl`, the
  notifications dialog on mobile, `SideTabPanel` overlays, tree menus
  opening left up to `md`, `ListSwitcher` icon-only at `md`, and
  `/app/note` redirecting to the dashboard in the SPA.
