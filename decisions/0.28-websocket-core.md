# 0.28 Websocket core

- Decided by: Claude (TODO item 2); user (size limits enforced while reading)
- Date: 2026-10-19

- `internal/app` creates one `websocket.Hub` and passes it to the HTTP
  server; workers will get it from there when items 7, 11 and 16 need
  `PushBackend`. `http.Server.RegisterOnShutdown` closes every connection
  with status 1001 (hijacked connections are not closed by `Shutdown`).
- Messages of one connection are handled in order on one goroutine fed by the
  read loop (queue of 16), so file chunks stay ordered and pongs are read
  while a handler is busy.
- No write mutex: coder/websocket allows concurrent writes (TODO item 2
  assumed otherwise).
- Size limits (1 MiB text, 2 MiB binary) are enforced while reading (user):
  the server reads at most one byte over the limit, answers with the parse
  error and drops the connection at once (`CloseNow`; `Close` would keep
  reading during its handshake). A websocket message cannot be skipped
  without reading it, so unlike the original the connection does not survive
  an oversized message; the browser reconnects. The library read limit stays
  at 2 MiB as a backstop. The error carries the request id when it can be
  read (also from the header of an oversized binary frame), otherwise a
  fresh one (0.7). Unparsable frames within the limits keep the connection.
- Handler errors reach the browser as they are only when they are a
  `websocket.ClientError` (including `Client.Require` permission errors) or
  `validation.Issues`; any other error is logged and answered with "Error
  while processing the request", so database and internal errors never leak.
  The original sent every error message.
- One handler per namespace/type; registering twice panics at startup.
- `Hub.RefreshUserSession(ctx, userID)` implements 0.4: rebuilds the session
  from the user row, rewrites all of the user's session rows, replaces the
  session (role, permissions) on every open connection and pushes
  `users/sessionUpdated` with the `/api/session` payload. `/api/process-step`
  uses it.
- Frontend: the app shell connects only when no required step is pending
  (the server rejects `/ws` until then) and shows "Loading application..."
  until the first connection. `users/sessionUpdated` replaces the user store
  session and re-runs the route guard, so a new required step or lost
  settings access redirects at once. `connect()` resolves after a successful
  retry and rejects after the last failed one or on `disconnect()`.
