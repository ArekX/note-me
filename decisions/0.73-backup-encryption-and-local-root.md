# 0.73 Backup encryption and the local backup root

- Decided by: user (`LOCAL_BACKUP_ROOT_LOCATION` as the root of every local
  target, target locations relative to it, no absolute paths; backups
  encrypted with `BACKUP_ENCRYPTION_KEY`, the server does not run without
  one; applies to all three databases); Claude (format and the rest)
- Date: 2026-10-21
- Amends 0.56.

Local targets:

- `LOCAL_BACKUP_ROOT_LOCATION` (default `backup` next to the executable,
  `backup` in the working directory for development, relative paths resolve
  against the working directory) is the only folder local targets can
  write to. A target's `location` is a folder name or a relative path inside
  it; absolute paths, `..`, and backslashes are refused ("Location must be a
  folder name inside the backup root, not an absolute path."). Targets
  stored by earlier builds with an absolute location no longer work until
  edited.
- The root and the target folders are created 0700, backup files 0600.

Encryption:

- Every archive is encrypted before it is saved: `encryption.EncryptFile`
  writes `NOTEME-ENC-1` || salt(16) || chunks of at most 64 KiB, each
  `uint32 length || nonce(24) || XChaCha20-Poly1305(chunk)`, with the chunk
  index and a last-chunk flag as additional data so chunks cannot be
  reordered, dropped or cut off. The key is Argon2id over
  `BACKUP_ENCRYPTION_KEY` with the archive's salt (parameters of 0.14).
  Backups are named `<automatic|manual>-<timestamp>.zip.enc`.
- `BACKUP_ENCRYPTION_KEY` is required: the server and `noteme-cli
  restore-backup` refuse to start without it. `.env.defaults` carries a
  development key; production sets its own, and a backup cannot be restored
  without the key that made it.
- Restore accepts both an encrypted archive and a plain zip from before this
  change.

Contents and disk:

- `session` rows are left out of every backup (sqlite: deleted from the
  `VACUUM INTO` copy, which is vacuumed again; PostgreSQL and MySQL: the
  table is not copied) and the target's `session` table is emptied on
  restore, so a backup never replays a cookie. `backup_target` rows stay,
  the archive is encrypted now. `audit_log` is backed up.
- The database snapshot is `chmod 0600` as soon as it exists; the temp
  folder is 0700.
- A manual backup claims the target before building the archive and archive
  builds are serialised with a mutex (SF-23). Backup handlers log the cause
  and answer fixed texts (SF-24).
- Restore validates the database entry first (SQLite header,
  `PRAGMA integrity_check`), bounds every entry by its declared size, stages
  files in a folder inside `FILES_LOCATION` and moves them into place after
  the database passed, and takes table and column names from the app's own
  schema, never from the archive (SF-26).
