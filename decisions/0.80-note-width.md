# 0.80 Wide or normal width per note

- Decided by: user (a per-note setting in the editor: wide, as before, or
  normal, centred at a maximum width for reading); Claude (details below)
- Date: 2026-10-21
- Amended by the user: new notes start at normal width (see the last
  point).

- New column `note.is_wide` (`boolean default true not null`) in the v2
  migration of every driver; new notes were wide at first (see below). `noteme-upgrade` adds it
  to older databases (`sqlite.UpgradeColumns`) with the same definition and,
  in the same transaction, sets the notes already there to normal width
  (user's choice); a database that already has the column is left alone.
  The app asks for the upgrade while the column is missing. Backups made before the column need
  the upgrade before a restore, like the other additions to the v2 schema.
- `createNote` and `updateNote` take an optional `is_wide` (absent on
  create meant wide, now normal); `getNote`, `getSharedNote`, the public note, restored
  notes and `createNoteResponse` return it. A width change on its own adds
  no history version and keeps `updated_at`, since it only changes the
  layout. Note history does not store the width.
- Editor: a toggle next to Protect (desktop only; on a phone both widths
  look the same) switches the layout at once and is saved with the note.
  Normal width is `.note-normal-width` in `notes.css`: 68rem, centred
  (first 52rem, widened by the user). The viewer, shared and public pages
  use the owner's setting. Placement: see 0.81.
- New notes are created at normal width: an absent `is_wide` on create
  means normal, and the new note editor starts with normal width; the user
  switches a note to wide. The column default stays `true`, since every
  insert sets the value and SQLite cannot change a column default in
  place.
