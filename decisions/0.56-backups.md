# 0.56 Backups

- Decided by: user (backups include the uploaded files and must be
  restorable); Claude (format, restore command and the rest, TODO item 19)
- Date: 2026-10-19

Format and restore:

- Since 0.3 uploaded files live on disk, so a database copy alone would lose
  them. Every backup is one zip, `<automatic|manual>-<yyyy-MM-dd-HH-mm-ss>.zip`
  (UTC): `manifest.json` (`format: 1`, creation time, version, file count),
  `database.sqlite` and `files/<identifier>` for every file in
  `FILES_LOCATION`. The database copy is made with `VACUUM INTO` (consistent
  even while the app writes, 0.9.q); files are stored uncompressed, the
  database compressed. A file deleted between the snapshot and the copy is
  left out.
- `noteme-cli restore-backup [--overwrite] <backup.zip>` restores with the
  server stopped, using the configured `DATABASE_DSN` and `FILES_LOCATION`
  without opening the database: files are written first (each under a
  `.partial` name, then renamed), then the database is written next to the
  target and renamed over it, after removing the old `-wal`/`-shm` files,
  which SQLite would otherwise replay onto the restored database. An
  existing database is only replaced with `--overwrite`. Files that are not
  in the backup stay. Entry names that would leave the files folder are
  refused. Migrations run as usual at the next start, so older backups work.
- Backups made by the original app (`.db` files) still show in the list and
  download; restoring one is copying it into place and running
  `noteme-upgrade`.

Running backups (`internal/components/backups`, on `components.Backups`):

- Targets implement `Setup`, `Save`, `Delete`, `Open`, `List` (newest first).
  **local** copies into the folder (via `.partial`). **s3** uses the AWS SDK:
  multipart upload (5 MiB parts, 4 at a time), key `<prefix>/<identifier>`,
  or just the identifier without a prefix (the original wrote
  `/<identifier>`; 0.63 also reads the original keys), listing every page (the original stopped at 1000 keys)
  and only objects directly under the prefix; `iam_role` uses the default
  credential chain, `access_key` the stored keys.
- A target is claimed with an atomic update of `is_backup_in_progess`, so a
  manual and an automatic backup never write to the same target at once;
  the flag is released when done and `last_backup_at` is set only on
  success. Stale flags are cleared once at server start (the original
  cleared them at every nightly run, wiping a running manual backup's flag).
- Nightly `backup-database` (midnight UTC): skipped when
  `MAX_ALLOWED_BACKUP_COUNT` is 0, there are no targets or the database is
  in memory. One archive is built and saved to every target; after each save
  the oldest `automatic-*` backups beyond the limit are deleted (manual ones
  never). A failing target does not stop the others, but the task now
  reports the failed targets as its error so Settings → Tasks shows it (the
  original logged and reported success).
- Backup names are checked with the original `^[a-zA-Z0-9.-]+$` and also
  refuse `.` and `..`, which the pattern let through.

Websocket `settings` (all need `canManageBackups`):

- Target validation follows `backupTargetSchema` with zod's union rule: the
  one branch whose fields have the right types reports its issues
  (`too_small` with paths like `settings.location`, `unrecognized_keys`);
  otherwise one `invalid_union` issue at the root.
- Fix: S3 secrets are never sent to the browser (`secret_access_key: ""` in
  every response); an update that leaves the secret empty keeps the stored
  one.
- Targets are set up (local folder created) before they are stored; the
  original stored first and then failed.
- `getBackupTargetsResponse` carries `max_backup_count`
  (`MAX_ALLOWED_BACKUP_COUNT`), which the page uses to say backups are
  disabled.
- `createBackupNow` runs outside the connection's message queue (a backup
  can take minutes) and answers when done; every failure, including "Target
  not found" and "Backup is already in progress", comes back as
  `{success: false, message}`.
- Update and delete are refused while a backup runs ("Backup is in
  progress. Cannot update target" / "... delete target"); deleting a target
  leaves its backups in place.

Download: `GET /api/settings/download-backup?identifier=&target_id=`
(authenticated, `canManageBackups`; moved from `/app/settings/...` like
0.53): 400 "Invalid backup name.", 404 "Backup target not found" / "Backup
not found", otherwise streamed as `application/octet-stream` with the name,
`Content-Length` when known and `Cache-Control: no-cache`.

Frontend: Settings → Backups (`BackupManagement`, `ManageBackupTargetDialog`
with Configure / Backup List, `BackupTargetForm` validating with
`backupTargetSchema`, `LocalSettings`, `S3Settings` with "Leave empty to keep
the stored secret", `BackupTargetList` with manual backup, download, delete
and the restore instructions). Mock mode serves backup downloads as an empty
zip.

`deps.go` is gone: every approved module is imported by real code.
