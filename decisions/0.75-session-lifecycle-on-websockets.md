# 0.75 Session lifecycle on websockets, shutdown and connection limits

- Decided by: user (logout, expiry, forced reset and password change must
  reach open connections; shutdown logs everyone out while draining;
  connection cap by environment, unlimited by default; hub pushes
  asynchronous); Claude (mechanics)
- Date: 2026-10-21
- Amends 0.4, 0.27, 0.28.

- `POST /api/logout` closes the user's websocket connections after deleting
  the session rows, and clears the cookie whether or not a valid session was
  sent.
- The hub re-checks every connection's session row once a minute (separate
  from the 30 s ping): a connection whose session is gone (logged out
  elsewhere, expired and removed) gets `users/forceLogoutResponse` and is
  closed.
- A message is refused while the connection's session has a required step
  ("Required step must be completed first"), so an administrator setting a
  new password cuts the user's open tabs off at once; the reset page uses
  HTTP.
- Changing the own password (profile or reset step) deletes the user's other
  sessions and closes their connections; the current browser session keeps
  working.
- `MAX_CONNECTIONS_PER_USER` (0 = unlimited) is enforced when a connection
  registers; one over the limit is closed with status 1008 "Too many
  connections".
- Every message to a browser goes through a bounded per-connection queue
  drained by one writer goroutine; a client that stops reading is closed
  when its queue is full, so pushes from workers and the event bus never
  block.
- A panic in a handler closes only that connection after logging and
  sending the generic error.
- Shutdown: the hub sends `forceLogoutResponse` to every connection, closes
  them and waits (bounded) for running handlers before the database is
  closed. Users sign in again after a restart.
- `http.Server` has an idle timeout and the JSON routes a 30 s handler
  timeout; the websocket, file, export and backup downloads have none.
