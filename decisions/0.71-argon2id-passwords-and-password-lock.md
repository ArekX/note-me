# 0.71 Argon2id passwords and the password attempt lock

- Decided by: user (no bcrypt in the app, only `noteme-upgrade` keeps it to
  convert old hashes; signed in password checks limited per user, 10 tries
  settable by environment, 24 hour lock, signing in still allowed); Claude
  (format, conversion of skipped users, what the lock covers)
- Date: 2026-10-21
- Amends 0.51 (the passkey registration password no longer counts against
  the address limit).

Password hashing:

- `user.password` holds a PHC string
  `$argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>` (16 byte salt, 32 byte hash,
  unpadded standard base64) made by `encryption.HashPassword`; the
  parameters are those of the note key (0.14) and the only ones
  `encryption.VerifyPassword` accepts. `golang.org/x/crypto/bcrypt` is
  imported only by `cmd/noteme-upgrade`.
- `VerifyPassword` derives the hash even when the stored value is not an
  Argon2id string (a missing user, a cleared password), so a sign in with
  an unknown username takes as long as one with a wrong password (SF-19).
- The sqlite column keeps its `varchar(60)` type (sqlite does not enforce
  it, 0.61); PostgreSQL and MySQL use `varchar(255)`.
- Passwords are at most 128 characters wherever one is set ("Password must
  have at most 128 characters"); signing in still has no length rule (0.19).

`noteme-upgrade` converts hashes with each user's password, which it already
asks for to convert legacy note keys (0.15): one prompt per user converts
both. A skipped user keeps nothing that verifies: their password is cleared
and `is_password_reset_required` set, and an administrator gives them a new
password in Settings → Users (which also makes a new note key, 0.9.t). The
server refuses a database with a non-Argon2id hash until the upgrade ran.

Password attempt lock (`loginguard.PasswordGuard`, `MAX_PASSWORD_ATTEMPTS`,
default 10):

- Keyed by user id, in memory. Every password a signed in user enters
  counts: `verifyOwnPassword`, `encryptText`, `decryptText`, `exportOwnData`,
  the old password of `updateProfile` and of the password reset step, and
  the password asked before a passkey is registered (0.50).
- After `MAX_PASSWORD_ATTEMPTS` wrong passwords in a row every one of those
  checks answers "Too many failed password attempts, password checks are
  locked for 24 hours." for 24 hours; a correct password resets the count.
  Signing in is not affected, so the user keeps their session and notes
  that are not protected.
- The lock covers every check, not only password change and passkey
  registration, because the other checks are the same oracle for the
  password (every call derives Argon2id over 64 MiB, which is also why the
  count matters).
- The lock is recorded in the audit log (0.74).
