# 0.55 Periodic tasks

- Decided by: Claude (TODO item 18)
- Date: 2026-10-19

- The scheduler keeps its state in `periodic_task_schedule`. On start it
  deletes rows of tasks that are no longer registered, continues known tasks
  from their stored `next_run_at`, and schedules new tasks (or rows without a
  next run) from now. A run missed while the server was down is due at once
  and fires a single time; the next run is then computed from the current
  time, as in the original.
- After every run the next run and the result are saved: success sets
  `is_last_run_successful` and `last_successful_run_at`, failure sets
  `is_last_run_successful = false`, `last_fail_reason` (the error text,
  "Unknown error" when empty) and `last_fail_run_at`; the other side's
  fields keep their last values. Due tasks run one after another, each
  error is logged on its own.
- A run interrupted by shutdown is not recorded, so it runs again after
  the restart. The original's shutdown hook (`storeScheduledTasks`) is not
  ported: it marked every task as successful at the shutdown time, and the
  schedule is already stored after each run.
- `task_identifier` has no unique index in the original schema, so rows are
  looked up before they are inserted (no migration needed).
- `remove-expired-sessions` (not in the original) is a registered task and
  shows in the list.
- Websocket: new `settings` namespace package with `getPeriodicTasks`
  (`canViewPeriodicTasks`); fields that were never set are `null`.
- Frontend: Settings → Tasks with `PeriodicTaskList` (Refresh button and a
  10 s refresh; only the first load shows the loader, so the table does not
  flash every 10 s). The status badge follows `is_last_run_successful`
  (0.9.w) and says "No runs yet" before the first run. The settings store
  uses the shared record types from `src/types/records.ts`. Mock fixtures
  use the real schedules (next minute, hour, midnight UTC).
