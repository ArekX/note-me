# 0.32 Group and tree handlers

- Decided by: Claude (TODO item 3)
- Date: 2026-10-19

- Websocket handlers live in `internal/http/websocket/handlers`, one file per
  namespace, registered by `handlers.Register(hub, repo)` (0.41 made each
  namespace its own package with `New(c).Register(hub)`).
  `internal/http/websocket/api.NewHub(components)` creates the hub and
  registers the handlers; `internal/app` only calls that (user).
- `createGroup`, `updateGroup` and `deleteGroup` answer with
  `Request.RespondToUser`: the response goes to every connection of the user
  with the request's id, so other tabs update their tree (0.6). The child
  `groups/deleteGroupResponse` and `notes/deleteNoteResponse` pushes of a
  recursive delete also go to every connection; `deleteGroupProgress` only to
  the requester. The original answered the requester only.
- Fixes over the original: a new or changed parent must be an existing group
  of the user ("Group does not exist!"); moving a group into one of its
  descendants is refused with "Group cannot be moved into its own subgroup"
  (0.9.x, a recursive CTE walking up from the new parent); updating or
  deleting a missing or foreign group answers "Group does not exist!"
  instead of silently succeeding.
- A recursive delete walks the levels breadth first; each level is one
  transaction (`DeleteGroupChildren`) and is followed by its pushes and a
  cumulative progress message, as the original did per level.
- `GetUserGroups`, `GetAllUserGroups` and `AssignNoteToGroup` are not ported
  yet: nothing in item 3 uses them (items 4, 5 and 16 do).
