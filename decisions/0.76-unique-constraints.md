# 0.76 Unique constraints and insert-or-ignore

- Decided by: user (fix the check-then-insert races with unique indexes and
  conflict-aware inserts; replace MySQL `INSERT IGNORE`); Claude (how, given
  MySQL's found-rows mode)
- Date: 2026-10-21
- Amends 0.55 (`task_identifier` now has a unique index) and 0.69.

- The single migration (0.61) gains unique indexes
  `note_reminder_note_user_index` (note_id, user_id),
  `note_share_user_note_user_index` (note_id, user_id),
  `note_tag_name_index` (name), `note_tag_note_tag_note_index` (tag_id,
  note_id) and `periodic_task_schedule_task_index` (task_identifier) in all
  three drivers. `noteme-upgrade` removes the duplicates an original database
  may hold (tags merged by name, the newest reminder and the oldest share
  and schedule row kept) and creates the indexes.
- `sqlrepo.insertIfAbsent` is the one way to insert a row that may exist:
  sqlite and PostgreSQL use `ON CONFLICT (...) DO NOTHING` and
  `RowsAffected`; MySQL runs the plain insert and treats error 1062 as "row
  exists". `INSERT ... ON DUPLICATE KEY UPDATE` was not usable there: the
  connection runs with `CLIENT_FOUND_ROWS` (needed so `RowsAffected` counts
  matched rows like the other databases) and in that mode an untouched
  duplicate and a fresh insert both report one affected row. A failed
  statement does not abort a MySQL transaction, so the error path is safe;
  on PostgreSQL it would, which is why that driver gets `ON CONFLICT`.
- `dialect.upsert` builds `ON CONFLICT ... DO UPDATE SET col = excluded.col`
  and MySQL's `AS "new" ON DUPLICATE KEY UPDATE col = "new".col` (8.0.19+,
  within the 8.4 requirement). Reminders and the periodic schedule use it.
- Tags: a name that exists answers "Tag with this name already exists."
  from the admin create and rename handlers; linking a note resolves names
  through `insertIfAbsent` and re-reads the row on a race.
